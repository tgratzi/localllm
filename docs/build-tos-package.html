Building the TOS package by hand

How to turn this repo into one file you can copy to a TOS machine and install with tos apps install. The steps take about 20–30 minutes, most of it downloading.

1. What you are building

A TOS machine has no access to the internet or to our image registries. So everything it needs has to arrive in a single file. You build that file in two stages:

  1. A Docker image that contains the model server (llama-server) and the Gemma model itself (about 5 GB). The model is baked in at build time, so the running container never downloads anything.
  2. A TOS package: one .tar file made by tupack, Tufin's packaging tool. It holds the Helm chart (the instructions that tell Kubernetes what to run) and a copy of the Docker image. tos apps install reads this file directly.

After installing, other apps in the cluster can reach the model at http://localllm:8080/v1. It is not reachable from outside the cluster.

2. What you need first

WhatWhy
Docker running (Docker Desktop on Windows/Mac, or Docker on Linux) Builds the image and runs the packaging tools.

Every command below runs from the root of this repo (the folder that contains the Dockerfile).

3. Step 1: Build the Docker image

scripts/build-image.sh

What happens:

  1. It first checks with Hugging Face that the exact model file pinned in the Dockerfile still exists and that its fingerprint (SHA-256) matches. This takes seconds, and it saves you from waiting through a 5 GB download only to fail at the end.
  2. It builds the image. The model download is the slow part: expect 5–20 minutes depending on your connection. The build checks the downloaded file's fingerprint again and refuses to continue if it doesn't match.

When it finishes you have an image called gemma-e2b-server:local. Check with:

docker images gemma-e2b-server

Building again later is fast. Docker reuses the downloaded model unless you change the model settings in the Dockerfile or clear Docker's build cache.

4. Step 2: Test the image (optional, recommended)

scripts/test-local.sh

This starts the image on your machine, checks that a request without the API key is refused, sends one real chat request and prints the answer, then starts it again with no network at all to prove the model is inside the image. It cleans up after itself.

Port 8080 must be free. If you already run the model locally with docker compose up, stop it first (docker compose down), or the test can't start.

5. Step 3: Get tupack

tupack is a single Linux program. You don't install it; you just need the file. Clone the repo that contains it, at the release tag this repo was tested with:

git clone --branch v0.5.5 --depth 1 https://github.com/tufin-ext-resources/baseimage7.git ../baseimage7

The file you need is ../baseimage7/src/scripts/tupack. If you already have baseimage7 cloned, use that copy.

It runs inside a Linux container, so this works from Windows and macOS as well.

6. Step 4: Package it into the .tar file

This step takes the image from Step 1 and the tupack file from Step 3 and produces the .tar you install on TOS. One script does all of it. You need to run one command, in the right kind of terminal.

4a. Open a bash terminal in the repo folder

  • Windows: open Git Bash (not PowerShell, not Command Prompt). In File Explorer, right-click the repo folder and choose Open Git Bash here, or start Git Bash and type the folder path with forward slashes, for example: 
    cd /c/Users/<you>/AntiGravityProjects/localllm
    PowerShell won't work. The command below sets a setting in front of the script name (TUPACK=...), and that only works in bash.
  • Linux, macOS or WSL: any terminal. cd into the repo folder.

Make sure Docker Desktop is running (its whale icon is in the taskbar and says "running").

4b. Check the two inputs are there

# The image from Step 1. You should see one line: gemma-e2b-server   local   ...
docker images gemma-e2b-server

# The tupack file from Step 3. You should see the file listed, about 42 MB.
ls -lh ../baseimage7/src/scripts/tupack

If either is missing, go back to Step 1 or Step 3. If baseimage7 is somewhere else on your disk, use that path in the next command instead of ../baseimage7.

4c. Run the packaging command

TUPACK=../baseimage7/src/scripts/tupack scripts/build-tupack.sh v0.1.0

The command has three parts:

PartMeaning
TUPACK=../baseimage7/src/scripts/tupack Tells the script where the tupack file is. No spaces around the =.
scripts/build-tupack.sh The packaging script in this repo.
v0.1.0 The version of the package you are making. Choose it yourself and increase it every time. It must look like v1.2.3; 1.2.3 and v1.2.3-rc.1 are also accepted.

It runs for 3–10 minutes. Leave the terminal open until you get the prompt back.

4f. What the script did for you

In order:

  1. Starts a temporary image registry on your machine. tupack can only read images from a registry, not from Docker's own list of images, so the script runs a throwaway one on 127.0.0.1:5000. It is only reachable from your own machine.
  2. Pushes your image into it (about a minute).
  3. Copies the Helm chart from charts/localllm and stamps your version number into the copy. The original in the repo is not changed.
  4. Runs tupack, which reads the chart, finds the image it uses, downloads it from the temporary registry, and writes everything into one .tar (3–5 minutes).
  5. Cleans up: removes the temporary registry and its working folder, even if a step failed.

Optional safety check: add TUPACK_SHA256=840e9de158e25975478aadec20bcc165bb98c49f5e4ce8b11b47be86cb82ab7f in front of the command. The script then refuses to run any tupack file other than the one from v0.5.5.

4g. Doing the same thing without the script (to understand it, or if the script fails)

These are the same steps the script runs, one command at a time. Run them in Git Bash or a Linux terminal from the repo folder. Use them to see exactly which step fails, or to adapt the process. For normal builds, use the script: it also checks your inputs and always cleans up.

1. Choose the version and start a temporary registry

VERSION=0.1.0
docker run -d --rm --name pkg-registry -p 127.0.0.1:5000:5000 registry:2

A registry is a server that stores images. tupack can only read images from one, so this starts an empty, temporary one on your machine.

2. Put your image into it

docker tag  gemma-e2b-server:local localhost:5000/localllm/gemma-e2b-server:$VERSION
docker push localhost:5000/localllm/gemma-e2b-server:$VERSION

docker tag gives the image a second name that says "in the registry at localhost:5000". docker push copies it there.

3. Make a working copy of the chart with your version number in it

mkdir -p dist/work/chart
cp -R charts/localllm dist/work/chart/
sed -i "s/^version:.*/version: $VERSION/; s/^appVersion:.*/appVersion: \"$VERSION\"/" dist/work/chart/localllm/Chart.yaml
sed -i -E "s/^(    version:).*/\1 \"$VERSION\"/" dist/work/chart/localllm/values.yaml

The first sed sets the chart's version, the second sets which image tag the chart asks for. Afterwards, grep version dist/work/chart/localllm/*.yaml should show your version three times.

4. Tell tupack where to find the image during the build

printf 'image:\n    registry: localhost:5000/\n' > dist/work/build-values.yaml
cp ../baseimage7/src/scripts/tupack dist/work/

The chart normally points at tos-registry.local, the registry inside TOS. This small file overrides that only while building, so tupack reads from your temporary registry. The packaged chart still says tos-registry.local, which is what TOS needs.

5. Run tupack

# Windows Git Bash only: stop Git Bash from rewriting the /w paths, and give Docker a Windows path.
export MSYS_NO_PATHCONV=1
WORK="$(cygpath -w "$PWD/dist/work" 2>/dev/null || echo "$PWD/dist/work")"

docker run --rm --network container:pkg-registry -v "$WORK:/w" -w /w ubuntu:24.04 \
  /w/tupack build \
    --name localllm --version "$VERSION" --type marketplace \
    --title "Local LLM (Gemma 4 E2B)" \
    --sha "$(git rev-parse --short=12 HEAD)" --no-progress \
    --build-values /w/build-values.yaml \
    chart/localllm/

tupack is a Linux program, so it runs inside an Ubuntu container. --network container:pkg-registry puts that container on the registry's network, so localhost:5000 inside it reaches the registry. This works the same on Windows, macOS and Linux. The result is dist/work/localllm.tar.

6. Name the file, record its fingerprint, clean up

mv dist/work/localllm.tar dist/localllm-$VERSION.tar
(cd dist && sha256sum localllm-$VERSION.tar > localllm-$VERSION.tar.sha256)
docker rm -f pkg-registry
rm -rf dist/work

Removing the registry also deletes the copy of the image that was pushed into it, about 5 GB of disk.

7. Step 5: Install it on the TOS machine

Copy both files from dist/ to the TOS machine (for example with scp), then on that machine:

# 1. Check the copy is complete. It must print "OK".
sha256sum -c localllm-0.1.0.tar.sha256

# 2. Install. For a machine that already has an older version, use "upgrade" instead.
tos apps install localllm-0.1.0.tar
# tos apps upgrade localllm-0.1.0.tar

# 3. Watch it start. Wait for 1/1 Running. Loading the model takes up to a few minutes.
kubectl get pod -l app=localllm -w

The TOS machine needs about 2 free CPUs and 6 GB of free memory. If the pod stays Pending, there isn't enough room; kubectl describe pod -l app=localllm says why.

To remove it: tos apps uninstall localllm. This also deletes the API key, so a later install gets a new one.

How other apps connect to it (address, API key, code example) is in kubernetes.md.

8. When something goes wrong

You seeWhat it means and what to do
image 'gemma-e2b-server:local' not found Step 1 hasn't been run, or the image was deleted. Run scripts/build-image.sh.
set TUPACK to the tupack binary You left out TUPACK=... in front of the command, or the path is wrong. Check the file exists.
is not a semantic version The version must look like v1.2.3. Words like latest or v1.2 are rejected.
temporary registry did not start or "port is already allocated" Something else uses port 5000. Pick another: put REGISTRY_PORT=5077 in front of the command.
no space left on device Docker's disk is full. docker builder prune clears old build cache (the next image build then downloads the model again). docker system df shows what uses the space.
SHA-256 mismatch during Step 1 The downloaded model isn't the expected file. Don't work around it. Run scripts/verify-model-file.sh to see what changed on Hugging Face.
sha256sum -c prints FAILED on the TOS machine The copy was cut short or damaged in transfer. Copy the .tar again.
Very slow packaging on Windows Normal. Writing 5 GB from Docker Desktop into a Windows folder is slower than on Linux. Give it 10 minutes.

9. Building a new version later

  • Same model, new version number (for example, you changed a chart setting): skip Step 1 and run Step 4 with the new version. Packaging always uses whatever gemma-e2b-server:local currently is.
  • Different model or llama.cpp version: change the pinned values in the Dockerfile, then run all the steps again. Install the result with tos apps upgrade.
  • Always increase the version number. Two different packages with the same version are hard to tell apart on the TOS machine.
  • Commit before building a release. The package records the Git commit it was built from. If you have uncommitted changes it records the commit with -dirty added, so you can tell later that it doesn't match any commit exactly.

Pushing a tag such as v0.2.0 to GitHub runs the same steps automatically and attaches the result to a GitHub Release, split into parts because GitHub limits each file to 2 GB. That needs the repository secret BASEIMAGE_TOKEN; see .github/workflows/release-tupack.yml.
